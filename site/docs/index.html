Vmseed / Docs

Getting started

Vmseed turns a YAML file in your project into a fully provisioned Linux dev VM, and gives you one CLI to build, start, stop, open and list those VMs on Windows, Linux or macOS.

The idea is simple: nobody hand-installs a dev box any more, and nobody ends up with a box that's subtly different from everyone else's. The machine is described in config, the config is committed, and the same command builds the same machine on every laptop.

Three commands get you from an empty folder to a desktop: vmseed init, vmseed create, vmseed open. The same commands work on Hyper-V, KVM through libvirt and Apple Virtualization.

Concepts

Project

Any folder you ran vmseed init in, usually the root of a code repository. A project describes one VM, or several.

The .vmseed/ folder

Where a project's config lives. Most of it is committed, so the whole team shares it:

your project
.vmseed/
  vm.config.yaml                # shared settings, committed
  vm.config.local.yaml          # your username and password hash, git-ignored
  vm.config.example.yaml        # every option, documented
  vm.config.local.example.yaml
  ssh_keys/                     # *.pub files here become authorized keys
  blueprints/                   # only if the project has its own blueprints
  .gitignore                    # keeps the local file and private keys out of git

Every command looks for .vmseed/ in the current folder and then each parent, the way git does, so vmseed start works from anywhere inside the project.

Your ~/.vmseed folder

Per user, never committed: the downloaded OS installers, the VM disks, and a registry of every project on this machine. It's in the same place on every operating system. Set VMSEED_HOME to move it. More below.

Blueprint

One operating system and how to install it unattended: where the installer comes from, the answer file, and the provisioning steps. Your VM is "this blueprint, plus your config", and nothing in the config is tied to one OS. See Blueprints.

Config layers

Settings are merged from several layers, each overriding the one before: Vmseed's defaults, the blueprint's defaults, vm.config.yaml, vm.config.local.yaml, the selected machine, and finally command-line options. Your local file only names what you want to differ. See Configuration.

Your first project

  1. Install and check your machine Install Vmseed. Nothing else to install: if this computer can't run VMs yet, vmseed init offers to set it up in the next step. vmseed doctor checks it any time, and vmseed doctor --fix sets it up on demand.
  2. Set up the project In your project folder, run vmseed init and answer the questions (what it asks).
  3. Adjust the config Open .vmseed/vm.config.yaml: CPUs, memory, the repositories to clone, the database. Every option is explained in vm.config.example.yaml next to it. vmseed config --validate checks your changes.
  4. Build it vmseed create downloads and verifies the OS installer, installs it unattended, and provisions the VM on first boot (what it does). vmseed create --render shows what would be built without touching anything.
  5. Use it vmseed open for the desktop, vmseed ssh for a shell, vmseed status --follow to watch provisioning finish, and vmseed list for every VM on your machine. vmseed stop gives the memory back.
  6. Commit the config Commit .vmseed/. Its own .gitignore keeps your local file and private keys out. A teammate runs vmseed init --import or just creates their own vm.config.local.yaml, then vmseed create.

How vmseed init works

available

vmseed init runs in the current folder and creates .vmseed/ there. It asks, in order:

  1. Project name. Defaults to the folder name. It becomes part of the VM name and the hostname, so it is checked to be hostname-safe: letters, digits and hyphens.
  2. Blueprint. A list of the built-in blueprints, any your project already has, and Create my own… (below).
  3. Username, full name and password, only if needed: if you saved a default user before, init offers to reuse it instead (below).

Then it writes the config files, the ssh_keys/ folder and a .gitignore, and registers the project in ~/.vmseed/projects.yaml so vmseed list can find it.

Last, it checks this computer can run VMs. If it can't yet, init lists what it would do and asks: on Linux, install QEMU, libvirt and the UEFI firmware, start libvirt and add you to the libvirt group; on Windows, turn on Hyper-V and add you to Hyper-V Administrators, then restart. Say no, or run init from a script, and it only tells you to run vmseed doctor --fix later.

It refuses to run if .vmseed/ already exists. vmseed init --force rewrites only the two example files, and never touches your vm.config.local.yaml.

What vmseed create does

available
  1. Plan. Loads every config layer and the blueprint, runs every check config --validate runs, and prints what it will build.
  2. Check the name. Stops if a VM with that name exists (use --force to rebuild) or if <hostname>.local already answers on the network.
  3. Install media. Finds the current point release from the vendor's checksum file, downloads it to ~/.vmseed/isos/ once, and verifies its SHA-256.
  4. Seed disk. Renders the unattended install (a kickstart for Rocky, RHEL and Fedora, cloud-init for Ubuntu) with the whole provisioning tree inside, and writes a small FAT32 disk labelled OEMDRV or CIDATA. No admin rights needed.
  5. Define the VM with the ISO and seed attached.
  6. Install. Boots it and waits for the installer to power it off, printing progress every two minutes. Watch it with vmseed open --console.
  7. Finish. Ejects the ISO, detaches and deletes the seed (it held your password hash), and attaches the data disks.
  8. Checkpoint and boot. Takes a clean-install snapshot of the finished machine before its first boot, so a broken tool install can be rolled back without reinstalling (--no-checkpoint skips it). Then it boots, and provisioning runs inside the guest: vmseed status --follow shows it.

A fresh build takes 15 to 40 minutes, most of it package downloads. A readable copy of everything sent to the guest is kept in the VM's build/ folder.

Getting into the VM

Vmseed makes its own SSH key in ~/.vmseed/ssh/ the first time you build, and adds it to every VM, so vmseed ssh, vmseed exec, vmseed logs and vmseed status work with no setup. It keeps its own known_hosts there too, so rebuilding a VM never triggers ssh's "host identification has changed" warning.

To log in from other tools, drop your own .pub file into .vmseed/ssh_keys/ before building. Each VM is published on your network as <hostname>.local; when that name doesn't resolve, Vmseed uses the address the hypervisor reports.

Create my own blueprint

Choosing Create my own… in init asks for a blueprint to start from and a name for yours, copies the built-in one into .vmseed/blueprints/<name>/, and sets blueprint: <name> in your config. It's the same as running:

terminal
vmseed blueprints new my-rocky --from redhat-rocky-workstation

Edit any file in the copy. Files you don't include fall through to the shared provisioning steps, so a custom blueprint can be as small as one changed file. See custom blueprints.

Users and passwords

The password you type is hidden, asked twice, and hashed immediately with SHA-512 crypt. Only the hash is written, to vm.config.local.yaml as passwordHash. The plain password is never stored.

After the first project, init asks whether to save the user as your default in ~/.vmseed/config.yaml. Next time it offers to reuse that user instead of asking again. Skip the questions entirely with --no-user and fill the local file in later.

To make a hash yourself, for example to paste into a config by hand:

terminal
vmseed hash

A plain password key still works, for older configs. Vmseed warns when one appears in the committed vm.config.yaml.

Init without prompts

For scripts and CI, give every answer as an option and add --yes:

terminal
vmseed init --name acme --blueprint ubuntu-desktop \
  --username dev --password-hash '$6$...' --yes

When there is no terminal to ask in, a missing answer is an error rather than a prompt.

Several machines in one project

A machines: block describes a small fleet. Each key is a VM, with its own blueprint and any settings that differ. They share a network, so each can reach the others as <hostname>.local.

.vmseed/vm.config.yaml
machines:
  ubuntu-gui:
    blueprint: ubuntu-desktop
    osVersion: '24.04'
    cpus:      6
    memoryGB:  12
  ubuntu-middleware-db:
    blueprint: ubuntu-server
    osVersion: '24.04'
    cpus:      4
    memoryGB:  12
    bootstrap:
      installDesktop:   false
      extraAptPackages: [postgresql-client, redis-tools]

Inside such a project, create, start, stop, restart, remove and status with no name act on all of its machines. Commands that need one VM (open, ssh, exec, logs, snapshot) ask you to name it: vmseed open ubuntu-gui.

Choosing a VM

  1. vmseed <command> <name> acts on the VM, machine or hostname with that name, from any folder: the current project first, then every VM Vmseed built, then every registered project.
  2. vmseed <command> inside a project acts on that project's VM (or all its machines).
  3. --all acts on every VM Vmseed built on this computer (on create, every machine of the current project).

Outside a project, with no name and no --all, the command stops and suggests vmseed list.

Where things live

~/.vmseed
~/.vmseed/                 # VMSEED_HOME moves it
  config.yaml             # your saved default user
  projects.yaml           # the project registry that vmseed list reads
  isos/                   # downloaded installers (iso.directory)
  ssh/                    # Vmseed's own key pair and known_hosts
  blueprints/             # downloaded blueprints (later releases)
  tmp/                    # scratch files
  vms/<name>/
    vm.json               # the VM's record: project, user, hypervisor
    build/                # what was sent to the guest, for review
    ...                   # disks (Hyper-V, macOS) and backend state

VM disks live here rather than in your project, so cloud sync and backups don't pick up files of 25 GB or more; vm.path puts them somewhere else. On Linux the disks go in a libvirt storage pool instead (/var/lib/libvirt/images by default), because the system QEMU can't read home folders. vmseed clean deletes cached installers and scratch files.

Bringing an existing config

To reuse the config files from another project, or from an old checkout of the PowerShell tool Vmseed replaced:

terminal
vmseed init --import path/to/other/folder

It copies vm.config.yaml and vm.config.local.yaml into .vmseed/. Relative paths in the config (copyFrom, postStartFile, token files) are relative to the project folder, the one holding .vmseed/. The PowerShell tool was removed before 1.0 and is still in the repository's git history.

Getting help

  • vmseed help, vmseed -h or just vmseed lists every command. vmseed help <command> or vmseed <command> -h explains one.
  • vmseed doctor checks your machine.
  • --verbose adds detail and stack traces to errors, which helps in a bug report, along with the output of vmseed --version.
  • Ask or report on GitHub Issues.
