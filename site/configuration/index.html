Vmseed / Configuration

Configuration

A Vmseed VM is described by YAML in your project's .vmseed/ folder: a shared file the team commits, and a local file that's yours alone.

.vmseed/vm.config.example.yaml, written by vmseed init, explains every option in place.

The files

FileHoldsCommitted?
.vmseed/vm.config.yamlThe team standard: blueprint, resources, toolchain, repos, databaseYes
.vmseed/vm.config.local.yamlYour own overrides: username, password hash, keys, tokens, pathsNo, git-ignored
.vmseed/vm.config.example.yamlEvery option with its explanationYes
.vmseed/vm.config.local.example.yamlEvery option you might override locally, commented outYes

Your local file only names what you want to differ; everything else falls through to vm.config.yaml. Keep tokens and passwords in the local file only.

Sections are tagged @user-editable (change freely) or @advanced (the default is right for almost everyone, and the comment says what changing it costs). Search for the tag when you're looking for somewhere to change something.

How layers merge

Lowest to highest. Each layer overrides the ones above it:

  1. Vmseed's built-in defaults
  2. the blueprint's defaults
  3. .vmseed/vm.config.yaml
  4. the blueprint's overrides (what the OS is: a headless blueprint turns the desktop off even if the shared file asks for one)
  5. .vmseed/vm.config.local.yaml
  6. the selected entry in machines:, if any
  7. command-line options

vmseed config prints the result, so you can see exactly what a build would use.

Relative paths in the config (copyFrom, hooks.postStartFile, githubTokenFile, isoPath and so on) are relative to the project folder, the one holding .vmseed/. They may also start with ~/ or use environment variables ($HOME, %USERPROFILE%).

Quick settings

The settings people actually change have flat names, so they can sit in one block at the top of the file instead of nested several levels deep. Each is a shortcut for exactly one full setting. Names are case-insensitive (cpus, Cpus and CPUS are the same), and an unknown name is an error, not silently ignored.

.vmseed/vm.config.yaml
blueprint:      ubuntu-desktop
osVersion:      '24.04'
projectName:    acme

cpus:           6
memoryGB:       12
diskGB:         25

timezone:       America/New_York
repos:          [git@github.com:acme/web.git]
reposRoot:      src

dbEngine:       postgres
dbVersion:      '17'
dbServer:       true
dbAdminer:      true

Every key, with its default and an explanation, is in vm.config.example.yaml.

Names and addresses

projectName names the work rather than the OS. The VM name and the hostname both default to <projectName>-<blueprint>:

yaml
projectName: acme
blueprint:   ubuntu-desktop
# VM name and hostname: acme-ubuntu-desktop
# address:              http://acme-ubuntu-desktop.local

With enableMdns on (the default), the VM announces that name on the network, so it is also the address you browse to, with no hosts file and no static IP. An explicit vmName or hostname wins, then a machines key, then the derived name. Names are checked as DNS labels (letters, digits and hyphens, at most 63 characters) before anything is built, and a build refuses a name that is already taken on the network.

Choosing the OS

blueprint picks the OS and osVersion its release. The version must match the blueprint, and the build refuses a mismatch rather than downloading a release that doesn't exist. Leave osVersion blank to use the blueprint's own. Quote Ubuntu versions ('24.04'), or YAML reads them as numbers. See Blueprints.

Machines

Each key under machines: is one VM, named after the key unless it sets its own name. Quick settings work inside it. Every machine shares one network, so they reach each other as <hostname>.local.

.vmseed/vm.config.yaml
machines:
  web:
    blueprint: ubuntu-desktop
    osVersion: '24.04'
  db:
    blueprint: ubuntu-server
    osVersion: '24.04'
    dbEngine:  postgres
    dbServer:  true

Each machine names its own blueprint and version, because a version at the top of the file only means something to one OS.

password vs passwordHash

vmseed init only ever writes passwordHash, a SHA-512 crypt hash, into the git-ignored local file. Make one yourself with vmseed hash.

A plain password is still accepted, for older configs, and is hashed at build time. Vmseed warns when it finds one in the committed vm.config.yaml, because anyone who can read the repository can read it.

During a build, the hash travels to the VM on a small seed disk. Once the OS is installed, Vmseed detaches the seed disk and deletes it, and the provisioning steps shred any secrets inside the guest once they're done with them.

Checking a config

terminal
vmseed config --validate     # every check create runs
vmseed config                # print the merged result
vmseed config --json         # the same, for scripts

Validation runs every check vmseed create runs: unknown keys (with "did you mean" suggestions), ranges, the blueprint and OS version, data disks, the database, files to copy, hooks, repositories and SSH keys. Warnings are all shown together; a missing user is a warning here and an error for create. vmseed create --render goes one step further and writes the exact files the installer will receive.
